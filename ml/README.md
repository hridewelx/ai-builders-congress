# ml/ — model workstream

Only this folder and `app/services/vision.py` / `app/services/detector.py` are
model work. Everything else must run on a CPU-only laptop, and the demo must
keep working with **no model files present** (the numpy autoencoder is the
fallback).

The frozen interface every other stream depends on:

```python
detect(image: np.ndarray) -> {
    "proposals": [{"type": str, "score": float, "box": [x1, y1, x2, y2], "raw_error": float}],
    "heat_png": bytes, "model": str, "threshold": float, "calibrated": bool,
    "quality": {...}, "note": str,
}
```

## What is built

| File | Purpose | Status |
|---|---|---|
| `data.py` | BDFD9 + staged set -> one canonical YOLO set; SHA-256/dHash dedupe; source train/valid/test preserved | done |
| `verify_split.py` | Proves no official test image (exact or near-duplicate) is in train/val | done |
| `model.py` | torchvision Faster R-CNN + MobileNetV3-Large FPN (BSD-3-Clause) | done |
| `train.py` | GPU training, AMP, cosine LR, per-epoch validation | done |
| `evaluate.py` | per-class AP@0.5, P/R, FP per clean view, view recall, per-source block | done |
| `calibrate.py` | single-temperature scaling, ECE before/after | done |
| `export_onnx.py` | fp32 ONNX export + parity check against PyTorch | done |
| `infer.py` | CLI: boxes on image files, optional annotated PNG | done |

`app/services/detector.py` selects the backend. `LOTLINE_DETECTOR=auto` (the
default) uses the trained ONNX model when present and falls back to the numpy
baseline. `LOTLINE_DETECTOR=onnx` is strict: a missing artifact or runtime
failure stops startup instead of silently downgrading. `LOTLINE_DETECTOR=numpy`
forces the baseline.

## Reproduce

```bash
PY=C:/Users/Hridoy_/AppData/Local/Python/pythoncore-3.14-64/python.exe

# 1. data (BDFD9 zip from data.mendeley.com/datasets/z49cc7zvfc/1, CC BY 4.0)
$PY -m ml.data build \
  --source staged=data/dataset/v1 --licence generated \
  --source bdfd9=data/raw/bdfd9/BDFD9 --licence "CC BY 4.0" \
  --out data/dataset/det_v2

# 2. prove the official test folder did not leak into train/val
$PY -m ml.verify_split --data data/dataset/det_v2 \
  --raw-test data/raw/bdfd9/BDFD9/test

# 3. train (GPU; use --workers 0 on Windows)
$PY -m ml.train --data data/dataset/det_v2 --epochs 6 --batch 4 --workers 0 \
  --out data/models/det_v2.pt --metrics data/models/train_metrics_v2.json

# 4. evaluate once on the held-out official test split
$PY -m ml.evaluate --checkpoint data/models/det_v2.pt \
  --data data/dataset/det_v2 --split test --score-threshold 0.5 \
  --out data/models/eval_test_v2.json --card docs/MODEL_CARD.md

# 5. calibrate on validation, export ONNX with a parity gate
$PY -m ml.calibrate --checkpoint data/models/det_v2.pt \
  --data data/dataset/det_v2 --split val --out data/models/calibration_v2.json
$PY -m ml.export_onnx --checkpoint data/models/det_v2.pt \
  --out data/models/det_v2.onnx --report data/models/export_report_v2.json
```

Artifacts land in `data/models/` (git-ignored). Commit the model card and the
metrics, never a hand-written number.

## Results

Every published number is generated by `ml.evaluate` from a named checkpoint and
split; see `docs/MODEL_CARD.md`. The old `det_v1` 0.867 headline is **retired**:
that dataset used a random re-split that read BDFD9's `test/` folder, so it was
never a held-out result.

| Split | mAP@0.5 | Precision | Recall | Note |
| --- | --- | --- | --- | --- |
| official test, BDFD9 only | **0.9474** | 0.776 | 0.867 | headline; held out, evaluated once |
| official test, pooled | 0.9561 | 0.819 | 0.895 | diagnostic only, never the factory estimate |
| validation (harder) | 0.7479 | 0.741 | 0.733 | honest second estimate; ONNX 0.7475 |
| validation + review-queue cap | 0.7326 | 0.768 | 0.733 | cost of the 6-proposal cap: 0.0149 mAP |

Split integrity: `ml.verify_split` compared 109 official test images against 450
train/val images and found 0 exact and 0 near-duplicate leaks. Calibration on
validation fit a temperature of 0.87 but **increased ECE** (0.1061 -> 0.1179),
so the runtime keeps raw scores and the card makes no calibrated-probability
claim. Parity: PyTorch 0.7479 vs ONNX 0.7475 (delta 0.0004, tolerance 0.01).

## ONNX runtime note

`torch.onnx` cannot reshape a zero-row ROI tensor, so ORT raises when the
detector finds nothing. `app/services/detector.py` treats exactly that failure
as "no proposals", which is the correct answer for a clean view. Any other ORT
failure falls back to the numpy baseline and records that in `note`.

## Non-negotiables

- No fabricated accuracy, no "ISO compliant" claim, no invented AQL table.
- Scores are not probabilities. The card reports ECE before and after calibration,
  including runs where calibration made ECE worse and was therefore rejected.
- The model never outputs a count, a severity or a decision. It only proposes.
